# Деплой, резервное копирование и эксплуатация

## 1. Архитектура развёртывания

- **Frontend:** Next.js на Vercel (или любой Node-хостинг).
- **Backend:** Supabase Cloud (PostgreSQL + Auth + Realtime).

> ⚠️ **Трансграничная передача (ст. 89 Цифрового кодекса КР).** Supabase Cloud и
> Vercel размещают данные вне Кыргызстана. Это осознанный остаточный риск (см.
> `docs/SECURITY.md`, раздел 9). Перед обработкой реальных ПДн обеспечьте
> правовое основание передачи. Безопасная альтернатива — self-hosted Supabase на
> инфраструктуре в КР; код и миграции переносятся без изменений.

## 2. Применение миграций

Порядок (SQL Editor или `supabase db push`):

```
0001_schema.sql
0002_functions.sql
0003_rls_and_views.sql
0004_seed_demo.sql      -- опционально, демо-данные
0005_public_extras.sql
```

Проверка после применения: прогнать `supabase/tests/security_checks.sql` —
должен завершиться `ALL SECURITY CHECKS PASSED`.

## 3. Переменные окружения (Vercel → Settings → Environment Variables)

| Переменная | Где взять | Клиент? |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Settings → API | да |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | там же | да |
| `SUPABASE_SERVICE_ROLE_KEY` | там же (секрет!) | **нет, только сервер** |
| `NEXT_PUBLIC_SITE_URL` | адрес прод-домена | да |

`SUPABASE_SERVICE_ROLE_KEY` не должен иметь префикс `NEXT_PUBLIC_` и не
попадает в клиентский бандл (защищено импортом `server-only`).

## 4. Сборка и запуск

```bash
npm ci
npm run build
npm start
```

Vercel выполняет это автоматически при пуше. Заголовки безопасности (CSP, HSTS,
X-Frame-Options и др.) задаются в `next.config.ts`.

## 5. Первый администратор

1. Supabase → Authentication → Users → создать пользователя (Auto Confirm).
2. SQL Editor:

```sql
insert into public.app_users (id, role, full_name)
select id, 'admin', 'Главный администратор'
from auth.users where email = 'ADMIN_EMAIL'
on conflict (id) do update set role = 'admin', status = 'active';
```

MFA для администраторов опциональна (можно включить в коде, см. `docs/SECURITY.md`).

## 6. Резервное копирование и восстановление

- **Supabase Cloud:** включите ежедневные бэкапы и, при необходимости,
  **Point-in-Time Recovery** (план Pro). Settings → Database → Backups.
- Периодически **проверяйте восстановление** на отдельном проекте (restore →
  прогнать `security_checks.sql`).
- Дополнительно: регулярный логический дамп

```bash
pg_dump "postgresql://postgres:PASSWORD@db.PROJECT.supabase.co:5432/postgres" \
  --no-owner --format=custom --file=refal_$(date +%F).dump
```

  Храните дампы в защищённом месте с ограниченным доступом; они содержат ПДн.

## 7. Хранение и удаление данных

- По завершении турнира **архивируйте** его (кнопка в настройках → статус
  `archived`).
- Контактные данные удаляйте, как только отпадает необходимость (очистка полей в
  карточке игрока удаляет строку контактов).
- Запросы на удаление/исправление обрабатывайте через раздел «Согласия и
  запросы» и фиксируйте в журнале.

## 8. План реагирования на инцидент (кратко)

1. **Обнаружение** — журнал (`/admin/audit`), мониторинг Supabase, обращения.
2. **Локализация** — отозвать/ротировать скомпрометированные ключи (anon,
   service-role, пароли админов), при необходимости отключить операторов.
3. **Оценка** — какие данные затронуты (особое внимание — контакты,
   несовершеннолетние).
4. **Уведомление** — проинформировать затронутых субъектов и, при наличии
   обязанности, регулятора в установленные сроки.
5. **Восстановление** — из проверенного бэкапа; подтвердить `security_checks.sql`.
6. **Разбор** — зафиксировать причину и меры предотвращения.
