# Безопасность и конфиденциальность — REFAL Basketball League

> Этот документ описывает реализованные меры и остаточные риски. **Никакая
> система не гарантирует абсолютную защиту** (спец. §11.10). Заявление о полном
> юридическом соответствии требует отдельной проверки юристом.

Ориентир: Цифровой кодекс Кыргызской Республики от 31.07.2025 №178 и подзаконные
требования к защите персональных данных.

## 1. Классификация данных

| Категория | Примеры | Доступ |
|---|---|---|
| Публичные | счёт, расписание, названия команд | все |
| Публичные по согласию | ФИО, индивидуальная статистика | все, только при активном согласии |
| Внутренние ПДн | ФИО без согласия, номер, позиция | админ (RLS); оператор — состав своего матча |
| Особо защищённые | телефон, email | только админ, отдельная таблица |

## 2. Раздельные правовые основания (§11.2)

Разделены четыре случая обработки:
1. внутренний учёт для организации турнира;
2. публикация ФИО (согласие `publish_name`);
3. публикация персональной статистики с привязкой к имени (`publish_stats`);
4. будущее использование — требует нового основания.

Согласие на участие ≠ согласие на публикацию ФИО.

## 3. Privacy by Default (§11.1)

- RLS включён на **всех** таблицах; у `anon` нет политик на базовые таблицы →
  прямой запрос к PostgREST возвращает 0 строк.
- Публичный сайт читает только `public_*` представления. Они выполняются с
  правами владельца и отдают лишь публикуемые поля.
- Закрытые поля не попадают в браузер ни в HTML, ни в JS, ни в API-ответе, ни в
  данных SSR — потому что соответствующих колонок нет в представлениях.

## 4. Система согласий (§11.3–11.4)

- Админ выпускает **одноразовый токен** (`create_consent_token`). Хранится только
  SHA-256-хэш; «сырой» токен существует лишь в ссылке/QR для игрока.
- Срок действия ограничен (`expires_at`), повторное использование запрещено
  (`used_at`).
- Страница `/consent/[token]` показывает версионированный текст и **изначально
  снятые** отдельные галочки для имени и статистики.
- Админ не может подтвердить согласие за игрока: фиксация идёт только через
  `record_consent` по знанию токена.
- Несовершеннолетние (`players.is_minor`) требуют подписанта `legal_guardian`
  (§11.5) — иначе функция отклоняет запрос.
- Доказательства согласия: игрок, цель, версия текста, время, способ, статус,
  дата отзыва. Избыточная техническая информация не собирается.

**Отзыв:** `revoke_consent` снимает активную запись; представления сразу
перестают отдавать имя/статистику (эффект немедленный, т.к. вычисляется на лету).

## 5. Контактные данные (§11.6)

Телефон/email: отдельная таблица `private_player_contacts`, RLS только для
админа, не входят ни в одно представление, не логируются, не экспортируются,
отсутствуют в демо-данных. Рекомендация к усилению: шифрование на уровне колонок
(pgcrypto/`pgsodium`) — отмечено как hardening.

## 6. Контроль доступа (§11.7)

Реализовано:
- аутентификация через Supabase Auth; **MFA обязательна** для админов
  (проверка `aal2` в `hasMfaAssurance`);
- операторы — только по приглашению (создаются админом, вход по учётке);
- RBAC + **RLS** на уровне Postgres;
- проверка прав в каждой `SECURITY DEFINER` функции;
- **CSP**, HSTS, X-Frame-Options=DENY, nosniff, Referrer-Policy
  (`next.config.ts`). `script-src` допускает инлайн-скрипты Next.js
  (`'unsafe-inline'`; в dev — ещё `'unsafe-eval'` для HMR). Усиление до
  per-request nonce (убрать `'unsafe-inline'`) — запланированный hardening;
  `object-src 'none'` и `frame-ancestors 'none'` уже закрывают основную
  XSS/clickjacking-поверхность;
- защита от IDOR: доступ определяется RLS/функциями по `auth.uid()`, а не по ID в
  запросе;
- защита от SQL-инъекций: параметризованные запросы Supabase + функции;
- идемпотентность LIVE-событий против дублирования.

Планируется/зависит от инфраструктуры:
- rate-limiting и защита от перебора паролей (Supabase Auth + сетевой уровень/
  edge); документируется при деплое;
- безопасная обработка загружаемых логотипов (валидация типа/размера, отдельный
  bucket, без исполнения) — при реализации загрузки.

**UI-скрытие не является защитой** — все ограничения продублированы в БД.

## 7. Безопасная БД (§11.8)

- Публичные и приватные сущности разделены; публичное чтение — только через
  представления.
- Анонимное чтение `players` и контактов запрещено (RLS + REVOKE).
- Принцип минимальных привилегий: `anon`/`authenticated` имеют GRANT только на
  представления и разрешённые функции.
- `audit_logs` — журнал админ-действий без ПДн и токенов.
- Контроль изменений статистики: события версионируются через `voided` + причина.

Требует настройки оператором БД:
- защищённые резервные копии и проверка восстановления (PITR в Supabase);
- политики хранения/удаления и обезличивания;
- план реагирования на инциденты.

## 8. Несовершеннолетние (§11.5)

Флаг `is_minor` → обязательный путь согласия законного представителя. До
подтверждения основания ФИО ребёнка не публикуется (нет согласия → представление
отдаёт нейтральный идентификатор).

## 9. Трансграничная передача (§11.9) — ОСТАТОЧНЫЙ РИСК

**Выбрана инфраструктура Supabase Cloud** (решение заказчика). Данные физически
размещаются вне Кыргызстана. Перед обработкой реальных ПДн необходимо:

- определить фактическую страну размещения и субобработчиков Supabase;
- обеспечить правовое основание передачи по ст. 89 Цифрового кодекса КР;
- оформить договорные и организационные меры защиты;
- уведомить игроков в тексте согласия (уже указано в `0004_seed_demo.sql`).

**Безопасная альтернатива:** self-hosted Supabase на инфраструктуре в КР —
весь код переносится без изменений (миграции и функции портируемы). Рекомендуется
при обработке данных несовершеннолетних или чувствительных контактов.

## 10. Чек-лист тестов безопасности (§11.10)

Автоматизируется в Этапе 6; текущий статус — проектный:

- [ ] анонимный посетитель не получает ФИО без согласия;
- [ ] анонимный посетитель не получает телефон/email;
- [ ] оператор не может открыть таблицу контактов;
- [ ] оператор не может менять чужие матчи;
- [ ] отзыв согласия обновляет публичные ответы API;
- [ ] прямой запрос к PostgREST не обходит RLS;
- [ ] смена ID в запросе не даёт доступ к чужим данным (IDOR);
- [ ] ошибки сервера не раскрывают секреты;
- [ ] повтор события не удваивает счёт.

## 11. Остаточные риски (прозрачно)

1. **Трансграничная передача** — см. раздел 9.
2. **Доверие к облаку** — компрометация провайдера/service-role ключа. Митигация:
   ключ только на сервере, ротация, минимум привилегий.
3. **Инсайдерский доступ админа** — админ видит внутренние ПДн по роли; действия
   журналируются в `audit_logs`.
4. **Шифрование контактов** на уровне колонок не включено по умолчанию —
   рекомендуется для продакшена с реальными контактами.
5. **Rate-limiting** зависит от сетевой/edge-настройки при деплое.
